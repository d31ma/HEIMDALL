Providers and capabilities

Five runtimes answer one model — and refuse, by name, what they cannot express.

The adapters

Docker Engine, Docker Swarm, Amazon ECS, Google Cloud Run, and Azure Container Apps. Adapters are the only code that knows a cloud exists, they call the cloud SDKs directly (never Docker's deprecated compose integrations), and every adapter passes the same conformance suite.

The honest matrix

Each adapter's Capabilities() answers what it can and cannot express, the published matrix is generated from those answers so it cannot go stale, and a plan that asks for something rejected fails with the offending service and the alternative named (HD0300). Highlights:

Metrics and logs are not universal

Three of the five runtimes answer instance metrics and logs: Docker Engine and Swarm from the agent's ring buffer and minute rollups, ECS from CloudWatch. Cloud Run and Azure Container Apps refuse both by design (HD0370, HD0383) and name the provider-native store to use instead — Cloud Monitoring and Azure Monitor. HEIMDALL never builds a time-series database, and it will not pretend to be one for a platform that already has a good one.

What a cloud target needs in config

A target's config map is how infrastructure hands the adapter the things HEIMDALL deliberately does not own — networking, roles, log destinations, and the load balancer.

Interruptible capacity

A target naming capacity_provider: FARGATE_SPOT schedules onto spare capacity at roughly a third of the price. Spot tasks are reclaimed with two minutes' warning and ECS reschedules them, which is the right trade for staging, preview and batch targets — and the wrong one for a target carrying traffic that cannot be dropped. It is opt-in per target: say nothing and the service keeps on-demand Fargate.

The capacity provider has to be enabled on the cluster before a service can name it, which is infrastructure's job, not HEIMDALL's.

Putting a load balancer in front of ECS

Terraform (or whatever owns your infrastructure) creates the load balancer, its listener, and a target group; the target's target_group_arn hands that group to the adapter, and the service that publishes a port is registered into it when the service is created.

targets:
  - project: shop
    name: prod-ecs
    provider: ecs
    region: eu-west-1
    endpoint: prod                      # the ECS cluster
    config:
      subnets: subnet-aaa,subnet-bbb
      security_groups: sg-web
      execution_role_arn: arn:aws:iam::123456789012:
        role/ecs-execution
      log_group: /ecs/shop/site
      target_group_arn: arn:aws:elasticloadbalancing:
        eu-west-1:123456789012:targetgroup/site/abc123

Two rules keep this honest. When more than one service publishes a port the adapter refuses to guess (HD0363) until load_balanced_service names the fronted one. And attachment happens at service creation: a service that already existed before you added the target group needs recreating to pick it up.

Never silently drop

The compose parser models a deliberate subset and decodes with unknown-field rejection: a directive HEIMDALL does not model fails by name and line at render time. What a modelled directive means per provider is the capability matrix's job at plan time. Between the two, nothing you wrote can quietly not happen.
