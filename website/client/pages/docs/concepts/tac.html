Core concepts

Five nouns explain the whole system: spec, revision, plan, operation, and drift.

DeploySpec — the canonical model

Compose files plus overlays plus secret references render into one provider-neutral type, the DeploySpec. It is validated on the way out, canonicalized to exactly one byte sequence, and content-addressed with SHA-256. Two properties are load-bearing: the same commit renders byte-identically on any machine, and there are no maps anywhere in the type — every collection is a sorted slice, so the hash cannot depend on iteration order. Reformatting a compose file produces the same revision.

Revision — the unit of history

A revision is one commit rendered to a spec, stored immutably. It is the audit spine and the rollback unit: rolling back re-applies a stored revision and never re-reads git, so a force-push cannot change what rolling back means.

Plan — the work, shown first

A plan compares the desired spec against what the runtime actually has and lists the operations that would close the gap — create, update, restart, delete, or noop, per service, each with a reason. A plan of pure noops is how Synced is decided. A compose directive the target runtime cannot honour fails the plan by name; nothing is ever silently dropped.

Operation — one record per sync

Every sync is one document that every phase writes into: pending, planning, applying, then succeeded, failed, or superseded. A crash leaves one record in a known state rather than four collections disagreeing. Live state, events, and rollups are projections folded from operations and can always be rebuilt; the audit log is deliberately not a projection — a log you can regenerate is a log you can rewrite.

Drift — one observation, two consents

The loop continuously reads live state back. A new commit and a container killed by hand are the same observation — the desired and live states disagree. The application's sync policy decides what happens next: automated consents to converging on a moved revision, self_heal consents to restoring the same revision when the runtime drifted underneath it.

Waves

Services deploy in waves ordered by depends_on, and a service can be pushed to a later wave explicitly with a label — useful for migrations that must land before the app:

services:
  migrate:
    image: ghcr.io/example/migrate:3
    labels:
      heimdall.wave: "1"
