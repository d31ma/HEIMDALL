The registry in git

One interactive act binds a root repository; after that, what applications exist is a reviewed commit.

Bind once

The registry follows the same claim as everything else: git is the truth. A tenant binds one root repository — through the web UI's Registry page or POST /api/v1/registry/bind — and that binding is the single interactive act. It can require signed commits, and it carries a prune switch that gates deletion.

The manifest

The root repository holds registry.yaml, declaring projects, repositories, targets, and applications by name. Unknown fields fail the sync by name; a dangling reference fails before anything is applied.

projects:
  - name: shop
repositories:
  - project: shop
    name: site
    url: ssh://git@forge/shop/site.git
    default_ref: main
targets:
  - project: shop
    name: local
    provider: docker
    endpoint: http://10.0.0.5:2375
applications:
  - project: shop
    name: site
    repository: site
    target: local
    path: deploy
    sync_policy:
      automated: true
      self_heal: true

How a sync behaves

  • Creates and updates converge the collections on the manifest, in dependency order, and an unchanged manifest makes zero changes.
  • Adoption: a document registered interactively becomes registry-managed when the manifest declares it — visibly, as an update in the sync record.
  • Deletion is prune-gated: with prune off, undeclared managed documents are counted as withheld, never silently removed.
  • One record per pass lands in the operations log with every change named.

One authority per document

A managed document refuses interactive mutation: editing it through the API answers 409 HD0272 with the root repository named. The change is a commit — with review, blame, and revert — like every other change to truth. Unbinding keeps the stamps deliberately; rebinding restores the authority.

What a manifest can never declare

Principals, roles, and grants (authorization is SESAME's), secret values (references only), and agent enrollment (pinned fingerprints only). A compromised root repository can misroute deployments — which its review process exists to catch — but cannot widen anyone's access, read a secret, or enroll an agent.

Disaster recovery

Restore the deployment directory, bind the root repository, sync. A second control plane pointed at the same root reproduces the same registry.
