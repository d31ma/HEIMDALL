The registry in git

One interactive act binds a root repository; after that, what applications exist is a reviewed commit.

Bind once

The registry follows the same claim as everything else: git is the truth. A tenant binds one root repository — through the web UI's Registry page or POST /api/v1/registry/bind — and that binding is the single interactive act. It can require signed commits, and it carries a prune switch that gates deletion.

The manifest

The root repository holds registry.yaml, declaring projects, repositories, targets, and applications by name. Unknown fields fail the sync by name; a dangling reference fails before anything is applied.

projects:
  - name: shop
repositories:
  - project: shop
    name: site
    url: ssh://git@forge/shop/site.git
    default_ref: main
targets:
  - project: shop
    name: local
    provider: docker
    endpoint: http://10.0.0.5:2375
applications:
  - project: shop
    name: site
    repository: site
    target: local
    path: deploy
    sync_policy:
      automated: true
      self_heal: true

The full field set

The example above is the smallest manifest that works. These are the fields a real one uses.

OnFieldWhat it does
repositoryurlWhere the repository lives. An ssh URL uses the control plane's own deploy key.
default_refThe ref applications track unless they name their own.
credential_refA secret reference for a private repository. Never a value.
require_signatureRefuse to render a commit that is not signed.
targetregion, endpointWhere the runtime is. endpoint is the ECS cluster, the GCP project, the ACA environment, or the Docker Engine address.
configWhat infrastructure hands the adapter — subnets, roles, log groups, the load-balancer target group. See Providers for the keys each one needs.
credential_refA secret reference resolving to the cloud credential. Empty means the ambient chain — instance role, workload identity, az CLI.
tagsFree-form labels; target groups select on them.
applicationpathThe directory holding compose.yaml.
refThe branch or tag this application tracks, overriding the repository's default_ref. This is how one repository serves several environments.
overlaysFurther compose file names inside path, merged over the base in order — compose's own override semantics.
variablesValues for ${VAR} interpolation at render time. Never secrets: these are stored in the manifest, in git, in plain sight. Secrets are ${secret:...} references resolved at apply time.
suspendedStop reconciling without deleting anything. The UI marks it.

One repository, several environments

An application is a declaration, not a directory — so the same compose file, tracked from different branches onto different targets, is how production and staging stay honest about each other. Promotion becomes a pull request between branches, and nothing about the two environments can drift apart except the commit each one is at.

applications:
  - project: shop
    name: site                 # tracks production
    repository: site
    target: prod-ecs
    path: apps/site
    sync_policy:
      automated: true
      self_heal: true

  - project: shop
    name: site-staging         # same file, own branch
    repository: site
    target: staging-ecs
    path: apps/site
    ref: staging
    sync_policy:
      automated: true
      self_heal: true

Each application gets its own doorway from infrastructure — its own target group and hostname — so staging is reachable without being production. HEIMDALL itself is deployed this way: production, staging, and a develop environment on a Docker host reached through an agent, all from one root repository.

What the manifest cannot declare

Principals, roles, and grants (SESAME decides those), secret values (references only), and agent enrollment (an agent is not a principal). Target groups are also not declarable today — they are registered through the API. A compromised root repository can misroute a deployment; it cannot widen access, read a secret, or enrol a host.

How a sync behaves

  • Creates and updates converge the collections on the manifest, in dependency order, and an unchanged manifest makes zero changes.
  • Adoption: a document registered interactively becomes registry-managed when the manifest declares it — visibly, as an update in the sync record.
  • Deletion is prune-gated: with prune off, undeclared managed documents are counted as withheld, never silently removed.
  • One record per pass lands in the operations log with every change named.

One authority per document

A managed document refuses interactive mutation: editing it through the API answers 409 HD0272 with the root repository named. The change is a commit — with review, blame, and revert — like every other change to truth. Unbinding keeps the stamps deliberately; rebinding restores the authority.

What a manifest can never declare

Principals, roles, and grants (authorization is SESAME's), secret values (references only), and agent enrollment (pinned fingerprints only). A compromised root repository can misroute deployments — which its review process exists to catch — but cannot widen anyone's access, read a secret, or enroll an agent.

Disaster recovery

Restore the deployment directory, bind the root repository, sync. A second control plane pointed at the same root reproduces the same registry.
