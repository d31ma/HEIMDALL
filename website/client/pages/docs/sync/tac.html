Sync, drift and rollback

The loop that closes the gap — and the levers an operator has over it.

Sync policies

Auto-sync and self-heal are one loop, not two. On each tick the loop reads every consenting application's status; a moved revision syncs under automated, drift under the same revision heals under self_heal. Automated operations record a reason code instead of a principal, so the audit trail says "the policy did this".

sync_policy:
  automated: true
  self_heal: true
  prune: false

Webhooks — a push is a nudge, not data

Point your forge at POST /api/v1/webhooks/<repo-id> with a shared secret (a reference, like every credential). The receiver verifies an HMAC over the raw body and never parses the payload — which branch moved is something the sync finds out by fetching. GitHub, GitLab, Gitea, and a plain curl from CI all work. Nudges are scoped to the pushed repository's applications and run in the loop's own goroutine, so a push storm coalesces instead of stampeding.

Plans, dry runs, selective syncs

A dry run produces the full plan and applies nothing. A sync can be narrowed to named services; pruning — deleting what the desired state no longer mentions — is always an explicit opt-in, marked in the plan.

Rollout strategy — compose's own vocabulary

How a service is replaced comes from deploy.update_config, not from a HEIMDALL extension. It is part of the revision's content hash, so changing a rollout strategy plans as an update.

services:
  api:
    image: registry.example.com/api:1.4.2
    deploy:
      update_config:
        order: start-first        # start-first | stop-first (default)
        failure_action: rollback  # rollback | pause (default) | continue
        monitor: 30s              # how long the replacement must stay healthy
        parallelism: 1
        delay: 5s

Swarm receives it as its own UpdateConfig. ECS receives it as a deployment configuration — start-first is 100%/200%, stop-first is 0%/100%, and failure_action: rollback enables the deployment circuit breaker, so AWS reverts a bad deployment on its own. Cloud Run and Container Apps always start the replacement first; stop-first is partial there and the matrix says so rather than pretending.

A standalone Docker Engine gets true start-first for a service with no published ports: the replacement starts under a scratch name, holds healthy for monitor, and only then is the old container retired and the name handed over. A service that does publish a host port cannot have two copies on that port, so start-first is rejected at plan time (HD0338) naming the port and the three ways out — front it with a proxy, run docker swarm init on the box, or state order: stop-first and accept the gap.

A sync is not done until the runtime has converged

After applying, HEIMDALL polls live state until every touched service reports healthy at the new revision, held for monitor. Applied means converged, not submitted. A rollout that never settles ends the sync Failed with the reason (HD0273) instead of reporting success that resurfaces minutes later as drift — and under failure_action: rollback the previous revision is re-applied from the immutable revision store, by content.

Rollback

A rollback re-applies a stored revision by content, never by ref. It cannot be affected by anything that happened in git since — including a force-push. In-repo (sops) secret ciphertext is pinned by the same commit, so a rollback decrypts exactly what its revision was rendered from.

Scheduled and batch workloads

A nightly backup is desired state like anything else. It is declared with x-heimdall-schedule on the service, and the schedule is part of the revision's content hash, so editing a cron expression plans as an update.

services:
  nightly-report:
    image: registry.example.com/reports:1.4.2
    command: ["./report", "--daily"]
    x-heimdall-schedule:
      cron: "0 3 * * *"       # omit for a manual-only batch job
      timezone: UTC           # defaults to UTC, never the host's zone
      concurrency: forbid     # forbid | allow | replace
      deadline: 15m           # a run that cannot start this soon is skipped
      timeout: 30m            # a run still going then is killed and failed
      retries: 2

A scheduled service is not a running service. ports, deploy.replicas, restart, healthcheck, depends_on, and deploy.update_config are rejected at render time on a job (HD0221), because each contradicts having runs instead of a steady state — on every runtime, so the refusal lives in render rather than four times over in adapters.

HEIMDALL never owns the clock. A control plane that owned a cron would miss runs across a restart and double-fire across an active/passive failover, so the schedule is registered with the runtime's own scheduler: EventBridge Scheduler on ECS, Cloud Scheduler in front of a Cloud Run job, an ACA job's Schedule trigger on Container Apps, and the heimdall agent on Docker Engine and Swarm — which keeps firing while the control plane is unreachable. A Docker target with no agent enrolled refuses a scheduled service at plan time (HD0340) rather than running it once and never again. Container Apps evaluates job cron in UTC only, so a job naming another timezone is refused (HD0383) rather than quietly moved by an hour.

Running one now. heimdall run --project P --app A --service S starts a single out-of-band execution — a re-run after a failure, or the only way a manual-only batch job (a schedule with no cron) ever runs. It has its own authorization action, app:run: an operator who may re-run last night's report should not thereby be able to deploy. On a Docker target the request travels to the agent that owns the clock; nothing about desired state changes.

Deleting a job deletes its schedule first. An orphaned rule fires at 03:00 forever against a stale image, so every adapter removes the registration before the workload, and the conformance suite asserts it. Drift for a job is read from the registration, not from a container: a cron expression edited in a cloud console shows up as drift like any other change.

An execution is an instance that stopped. A finished run carries its exit code and finish time, so per-instance logs and the revision link work for jobs without a second shape — and the instance page grows a Runs tab with a duration trend and one row per execution.

Offline targets park, then drain

A sync for a target whose agent is offline parks as a durable pending intent (bounded per target, 24-hour TTL). On reconnect the host runs one fresh sync that re-reads git — an hour of missed commits converges to the newest revision instead of marching through every intermediate one, and superseded intents close pointing at their replacement.
