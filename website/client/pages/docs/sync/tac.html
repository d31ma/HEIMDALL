Sync, drift and rollback

The loop that closes the gap — and the levers an operator has over it.

Sync policies

Auto-sync and self-heal are one loop, not two. On each tick the loop reads every consenting application's status; a moved revision syncs under automated, drift under the same revision heals under self_heal. Automated operations record a reason code instead of a principal, so the audit trail says "the policy did this".

sync_policy:
  automated: true
  self_heal: true
  prune: false

Webhooks — a push is a nudge, not data

Point your forge at POST /api/v1/webhooks/<repo-id> with a shared secret (a reference, like every credential). The receiver verifies an HMAC over the raw body and never parses the payload — which branch moved is something the sync finds out by fetching. GitHub, GitLab, Gitea, and a plain curl from CI all work. Nudges are scoped to the pushed repository's applications and run in the loop's own goroutine, so a push storm coalesces instead of stampeding.

Plans, dry runs, selective syncs

A dry run produces the full plan and applies nothing. A sync can be narrowed to named services; pruning — deleting what the desired state no longer mentions — is always an explicit opt-in, marked in the plan.

Rollback

A rollback re-applies a stored revision by content, never by ref. It cannot be affected by anything that happened in git since — including a force-push. In-repo (sops) secret ciphertext is pinned by the same commit, so a rollback decrypts exactly what its revision was rendered from.

Offline targets park, then drain

A sync for a target whose agent is offline parks as a durable pending intent (bounded per target, 24-hour TTL). On reconnect the host runs one fresh sync that re-reads git — an hour of missed commits converges to the newest revision instead of marching through every intermediate one, and superseded intents close pointing at their replacement.

Fleet fan-out

Syncing an application that names a group produces one operation per member, run with bounded concurrency, under an umbrella record that reports the whole rollout. Members are processed in a stable name order, so a fan-out that fails is reproducible rather than a lottery.

A failure threshold halts the rollout: past it, no further hosts are started. Halting means exactly that — in-flight syncs run to completion, because killing a half-applied host to signal a problem creates a second problem. Each member's own operation document records what happened there, so "which of the fifty failed, and why" is a query rather than an investigation.
