One loop, four mechanics

ArgoCD's mechanics, applied to compose: your repository declares the desired state, the control plane keeps reading the live state back, and anything that makes the two disagree becomes a plan.

1 — Declare

Compose files and overlays in git render into one canonical, content-hashed DeploySpec. Reformatting is not a change; a force-push cannot rewrite history you already deployed.

2 — Plan

Every sync shows its work first: create, update, delete, per service, with the reason. A compose directive a runtime cannot honour is rejected by name at plan time — never silently dropped.

3 — Apply

Waves ordered by depends_on, secrets resolved at the last moment and never persisted, registry credentials used inside one call. One operation document records the whole story.

4 — Observe

Continuous live-state read-back. A new commit and a container killed by hand are the same observation — drift — and auto-sync and self-heal are the same loop answering it.

Built like it has to answer for itself

An honest capability matrix

Each adapter answers what it can and cannot express, and the published matrix is generated from those answers. Replicas on a standalone Engine? Rejected, with the alternative named.

Rollback that means it

A rollback re-applies a stored, immutable revision. It never re-reads git, so a force-push cannot change what rolling back means.

Agents for hosts you cannot dial

Outbound-only agents over mTLS with fingerprint-pinned enrollment. An agent is not a principal: it holds no grant and receives only the work an authorized sync produced.

Secrets are references

SOPS-encrypted files in your own repo, AWS Secrets Manager, Azure Key Vault, GCP, or a local sealed store. Values resolve at apply time, inside one call, and are never persisted or logged.

Dashboards, not a database

A resource tree, per-instance Grafana-style dashboards with deploy markers, and tailing logs — from provider-native metrics and bounded rollups. Deliberately not another time-series database.

The registry lives in git too

Bind one root repository and declare projects, repositories, targets, and applications in a reviewed manifest. One interactive act; every change after it is a commit.

Authorization is someone else's whole job

HEIMDALL writes no authentication or authorization logic — no password hashing, no session table, no role checks in handlers. SESAME, a dedicated security engine, decides every question exactly once, at the boundary, and an errored or unrecognised decision is a deny.

  • One Decide per mutating route; handlers receive already-authorized requests
  • An authoritative audit log — not a projection anyone could rebuild, and so rewrite
  • Sessions live in httpOnly cookies; the web tier holds no authority and makes no decisions
  • Webhooks verify an HMAC and never parse the payload — a push is a nudge, not data
